# Project Rules

A structured place to keep rules for AI agents (Claude, Codex, etc.) as your project
grows, instead of one giant prompt or a stale wiki page.

This folder is a blank starting point — one worked example rule instead of a full
set, and TODOs everywhere something needs project-specific input. Copy it into your
project (commonly `.claude/skills/<some-name>/`), rename the folder to whatever you
like, and fill in the TODOs.

**Before anything else:** if you rename this folder, keep three things pointing at
the same name — the folder itself, the `name:` field in `SKILL.md`'s frontmatter,
and the path in the pre-commit hook example below. A mismatch between the folder's
real name and a hardcoded path elsewhere (easy to introduce if you copy this into
several projects and rename each copy differently) is the most common way this setup
silently breaks: `node`/husky fails with "module not found" because the path points
at a folder that isn't actually there.

## Structure

- `rules/` — one markdown file per rule
  - `_sections.md` — maps filename prefixes to sections (title, impact, order) —
    the source of truth; TODO: adjust the starting categories to your project
  - `_template.md` — copy this to start a new rule
  - `<prefix>-<description>.md` — an individual rule (one example is included:
    `styling-colors-from-theme.md` — delete it once you have real rules of your own)
- `src/` — the build/validate scripts (plain Node, no dependencies, callable from
  anywhere — e.g. from your own husky pre-commit hook)
- `metadata.json` — document metadata (title, version, abstract) used by the build
- `SKILL.md` — the entry point Claude loads; short index + pointers into `rules/`
- `AGENTS.md` — compiled output (generated by `npm run build`, don't hand-edit;
  doesn't exist yet until you run the build once)

## Getting Started

1. Edit `SKILL.md`'s frontmatter (`name`, `description`) and the TODOs in
   `metadata.json` for your project. The `description` is what decides whether an
   agent opens this file at all, so be concrete about the stack and when to use it —
   see the TODO comment already in `SKILL.md` for guidance on writing a description
   that won't need editing every time you add a rule.
2. Edit `rules/_sections.md` to match the areas your project actually needs —
   add, remove, or rename rows. The `Prefix` column drives everything.
3. Write rules as you go (see below), then run `npm run build && npm run validate`
   (or wire that into your own pre-commit hook — see below).

## Wiring This Into Your Own Pre-Commit Hook

This folder doesn't manage git hooks itself — that's a project-wide concern, so
it belongs in your project's own husky (or equivalent) setup, not duplicated
here. `src/build.js` and `src/validate.js` resolve their own paths from
`__dirname`, not the current working directory, so they work correctly no
matter where in your repo this folder lives or where the hook runs from — just
point at them directly. Replace `<skill-folder>` below with whatever you actually
named this folder (matching the reminder at the top of this file):

```sh
# .husky/pre-commit
node .claude/skills/<skill-folder>/src/validate.js || exit 1
node .claude/skills/<skill-folder>/src/build.js || exit 1
git add .claude/skills/<skill-folder>/AGENTS.md
```

If your project also lints staged files (e.g. via `lint-staged`), that's a separate,
project-wide concern too — put it in the same `.husky/pre-commit`, before or after
these lines, rather than folding it into this skill's own scripts.

Add a check on `git diff --cached --name-only` first if you want the two lines above
to run only when `rules/` actually changed, rather than on every commit.

## Adding a Rule

1. Copy `rules/_template.md` to `rules/<prefix>-<short-description>.md`, where
   `<prefix>` matches a row in `_sections.md` (e.g. `architecture-`, `data-`).
2. Fill in the frontmatter (`title`, `impact`, optionally `impactDescription` and
   `tags`) and the body — a short explanation plus an Incorrect/Correct example.
3. Optionally add one line for it under **Quick Reference** in `SKILL.md` — this is
   a convenience for humans skimming the file, not something the agent depends on,
   so it's fine to let it fall behind.
4. Run `npm run build && npm run validate` (or let your pre-commit hook do it).

Rules are sorted alphabetically by title within their section — you don't manage
numbering by hand, `npm run build` assigns it (1.1, 1.2, ...).

## Impact Levels

Used for both sorting/prioritizing and for signaling how much a rule matters:

`CRITICAL` — highest priority, major correctness/perf/security impact.
`HIGH` — significant impact.
`MEDIUM-HIGH`, `MEDIUM`, `LOW-MEDIUM` — moderate impact.
`LOW` — incremental, nice-to-have.

`npm run validate` rejects any other value, so pick one of these six.

## Why Keep Rules as Separate Files Instead of One Big Doc?

So an agent (or you) can read exactly the rule that's relevant to the current task
— a few dozen lines — instead of loading the whole compiled document every time.
`AGENTS.md` still exists as a single-file fallback/overview, but `SKILL.md` points
agents at individual `rules/*.md` files first, and tells them to check
`rules/_sections.md` for what currently exists rather than relying on a snapshot
list — so `SKILL.md` itself doesn't need editing every time you add a rule inside an
existing category. Keep `AGENTS.md` in sync by always running `npm run build` after
editing `rules/`.

## Scripts

- `npm run build` — compile `rules/*.md` into `AGENTS.md`
- `npm run validate` — check every rule file has required frontmatter, a known
  prefix, and both an Incorrect and a Correct example
- `npm run dev` — build then validate
